# 架构设计

## 设计目标

系统同时满足两个目标：一是无需外部服务也能在答辩现场运行；二是可以切换到论文所描述的 Qdrant 与 Neo4j 架构。因此，向量存储、图谱存储、嵌入和生成模型都通过小型接口解耦。

## 离线索引流程

1. `DocumentParser` 根据扩展名解析文档，并保留 PDF 页码。
2. `TokenChunker` 将文档按 Token-like 边界分块，保留源文本的字符布局。
3. `Embedder` 为每个文本块生成向量。
4. `VectorStore` 保存向量、原文和来源元数据。
5. `FinancialEntityExtractor` 识别公司、机构、行业、政策和事件。
6. `GraphStore` 保存有方向的实体关系及其证据块 ID。
7. `DocumentCatalog` 保存文档级索引状态。

同一文件以内容 SHA-256 摘要作为 `doc_id`；重复索引采用 upsert，不重复创建文档记录。

## 在线问答流程

### 向量检索

问题被转换为向量，然后在指定文档范围内执行余弦相似度检索。若文档包含发布日期，检索器会加入上限为 0.03 的时效奖励。

### 图谱检索

系统先从问题中定位实体，再从实体出发扩展一至两跳关系。每条关系都保留 `chunk_id` 和 `doc_id`，因此图谱结论可以回到原始文本证据。

### 融合检索

向量得分与图谱置信度并不处于同一量纲，系统不直接相加，而是使用 Reciprocal Rank Fusion：

```text
RRF(d) = Σ  weight(channel) / (60 + rank(channel, d))
```

向量通道权重为 1.0，图谱通道权重为 0.9。最终证据仍需由答案生成模块逐项引用。

## 存储结构

### 向量记录

- `chunk_id`
- `doc_id`
- `content`
- `title`
- `source`
- `page_number`
- `publish_time`
- `chunk_index`
- `embedding`

### 图谱记录

- 源实体、源类型
- 有方向的关系类型
- 目标实体、目标类型
- 关系置信度
- 原始 `chunk_id` 和 `doc_id`

Neo4j 使用统一的 `FinancialEntity` 标签与 `RELATES` 关系类型，业务关系保存在 `relation` 属性中。这种方式避免动态拼接 Cypher 关系类型。

## 可靠性边界

- 默认规则抽取器强调透明和可测试，不追求覆盖所有金融实体。
- 哈希嵌入是离线后备能力，不等同于训练后的语义嵌入模型。
- 抽取式回答器只整理证据；接入大模型后仍由系统 Prompt 约束其引用证据。
- 当前没有自动爬虫或实时行情，所有回答只基于已索引材料。

## 推荐生产化改进

- 接入经过许可的财经新闻或公告数据源。
- 增加股票代码、公司别名和机构名称归一化。
- 加入文档版本管理、去重、撤回公告处理和时间有效区间。
- 用人工标注集评估 Context Recall、Citation Precision、Faithfulness 和答案正确率。
- 增加访问控制、审计日志、限流和敏感文件加密。
